# Security policy

## Reporting a vulnerability

Please do **not** open a public issue. Report privately through GitHub: **Security → Report a vulnerability** in this repository. You will get an answer within 7 days.

## Supported versions

Only the latest release receives fixes.

## Areas of particular interest

- **Imported content is untrusted.** Recipes come from arbitrary websites and social media. Anything that lets imported text execute code, inject markup into the plugin view, or steer an AI processor into actions beyond writing one recipe note (prompt injection) is a security issue.
- **Feedback on a recipe (#120).** The user's feedback is their own text, but it is still handled as data: it goes to the own AI only in the user message, never in the system prompt, next to the page text and the note's recipe (which was imported from the web earlier and is declared as data in the system prompt too). The three blocks carry a random nonce in their names (`<feedback-7f3a9c…>`, one per request), and in all text that is not ours every `<` (also the fullwidth and small forms) and every invisible format character is neutralised, so no text can close or fake a block; the recipe goes as JSON with `<` escaped (`src/feedback.ts`). **What this does not do:** a model can still be talked into following text inside a block; the answer is therefore never trusted: it must be one schema.org Recipe as JSON and goes through the same checks as every import (`recipeFromAnswer`, `recipeNote`), is shown as a change list with the new text of every changed part, and nothing is written before the user confirms (a backup comes first). The prompt tells the AI to leave what the feedback does not concern unchanged, but that is an instruction, not a guarantee; the new text of each part is shown so the user can check it. For Claude and GitHub the feedback is sent as `hinweis` (one cleaned paragraph, at most 1000 characters) with an improvement job; processors treat it as information from the user that may correct facts, never as instructions to change the task, and a workflow must hand it to scripts only through `env:` ([import contract](docs/import-contract.md)). Tests: `tests/feedback.test.ts`, `tests/aiFeedback.test.ts`, `tests/processorFeedback.test.ts`.
- **Tokens.** Anthropic, GitHub and AI keys must only live in Obsidian's secret storage and only be sent to the service they belong to (the AI key only to the address configured for it).
- **Own AI.** Pasted text and page text go to the configured AI clearly marked as untrusted material, with instructions that text inside it cannot change the task (`src/ai.ts`). The answer is never trusted either: it must be one schema.org Recipe as JSON and goes through the same sanitizing as a page's own recipe data (`recipeFromSchema`, `recipeNote`), sizes are capped, and images from the answer are never fetched. Tests with hostile answers: `tests/ai.test.ts`.
- **Vault writes.** The plugin may only change recipe notes in the recipe folder, and only the fields documented in [docs/architecture.md](docs/architecture.md). The local website import may only create one new note and its cover image there, never overwrite a file.
- **Local website import.** Page text goes into the note only as plain text: HTML is stripped, and every line is neutralized so it cannot add frontmatter, headings, embeds (`![[…]]`), wikilinks or HTML tags. Only http(s) images of known image types up to 15 MB are saved, and only from public hosts: image addresses pointing to `localhost`, local host names or private, loopback, link-local or multicast IPs are not fetched (`src/network.ts`), so a hostile page cannot make the plugin send requests into the user's network. Redirects are followed by Obsidian and cannot be checked. Backticks, Markdown links, Templater commands (`<%`) and action addresses (`obsidian://`, `javascript:` …) are neutralized too, so the note contains nothing that Templater, Dataview or other plugins could run. Tests with hostile pages: `tests/schemaorg.test.ts`, `tests/importCheck.test.ts`.
- **Social media import.** The plugin reads the public page of a post (`src/socialImport.ts`). The page and the caption are untrusted like any page: only the caption text, a cover image address and up to three links are cut out (nothing is run, no HTML is rendered), the caption goes through the same path as pasted text (offline rules or the own AI, marked as untrusted material) and `recipeNote` neutralizes every line. The page must be the post that was asked for (the ID of the post is checked against the page for Instagram, TikTok, YouTube and Pinterest; a login wall or another post gives nothing). The links in a post are followed only if the caption holds no recipe and the setting "Rezeptseiten selbst lesen" allows reading websites in the plugin, at most three, as http(s) and as a public address (`src/network.ts`, checked before each request); image addresses are checked like those of websites (see the next point). Requests are single and user-started, for the one link (Instagram: a second one on its embed page), without login, cookies or tokens. Instagram gets the headers of a mobile browser (`User-Agent`, `Sec-Fetch-Mode: navigate`), otherwise it does not answer with the caption. **Grey area:** the platforms' terms of use forbid automated collection. This import is the narrowest form of it (a single request the user starts for their own recipe collection, logged out, without getting around tokens or paywalls), but it remains a grey area and the user decides on using it; processors stay an option. Tests: `tests/socialPage.test.ts`, `tests/socialFlow.test.ts`, `tests/socialOutcome.test.ts`.
- **Link in a caption.** A caption can contain any address. The plugin follows at most three of them, only when the caption holds no recipe itself, only public addresses of other sites, never an address of a platform and never a known short link or "link in bio" service (`src/shortLinks.ts`, tests in `tests/socialPage.test.ts`). For Pinterest the link is the one of the pin object with the pin's own ID, never that of a related pin; without a sure pin ID (after a `pin.it` redirect it comes from `og:url` or the canonical address of the loaded page) no link is followed. The reason: Obsidian follows redirects itself and where they end cannot be checked, so a short link could lead to a host on the user's network. The linked page is read like any recipe website (schema.org only, no AI, same neutralizing). An address already in the collection is not fetched again. The note's source is then the linked recipe website, not the post.
- **Timeline graphic.** The SVG of an import (the `Ablauf` graphic of a note) is parsed and inserted as DOM nodes, never as HTML (`src/ui/svg.ts`, `src/ui/shared.tsx`). Attack surface: script, external requests, and spoofing the plugin's interface with a large or styled graphic. Allow-lists: only SVG drawing elements in the SVG namespace (no `style`, `script`, `image`, `use`, `foreignObject`, `a`, animation); only listed geometry and presentation attributes in no namespace (no `style`, no event attributes, no links); paint attributes accept only colors, `none`, `currentColor` and a local `url(#id)`; `class` only tokens of the palette (and none on the root); `id` gets a prefix per graphic; `aria-label` and `aria-hidden` only; comments, processing instructions and CDATA are removed; input with `<!DOCTYPE` or `<!ENTITY` is rejected. The container clips and contains the graphic (`.rz-ablauf` in `src/plugin.css`). Tests: `tests/svg.test.ts`.
- **Notes from processors.** Notes written by a processor (Claude, GitHub workflow) are checked when they arrive (`src/importCheck.ts`): Templater commands, code blocks, inline Dataview queries, active HTML, links that trigger actions and embeds of notes are reported as a warning and on the recipe page. The plugin does not execute or render any of it itself; the check protects against other plugins acting on the note. Requirements for processors: [docs/import-contract.md](docs/import-contract.md#security-requirements-for-processors).
